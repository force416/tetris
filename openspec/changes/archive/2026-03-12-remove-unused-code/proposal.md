## Why

目前專案已具備最小可玩核心，但仍存在未被引用的型別、常數、欄位、輔助函式或已失效的實作路徑風險，會增加閱讀成本並讓後續變更更難判斷真實依賴。趁專案規模仍小時先整理這些殘留代碼，可以降低維護負擔，避免未來在核心規則、渲染與輸入調整時被過時結構誤導。

## What Changes

- 盤點並移除目前程式碼中未被引用的代碼、無效欄位、無用途設定值與死路徑。
- 在不改變既有玩法結果的前提下，整理 `internal/game`、`internal/app`、`internal/input`、`internal/render` 與 `cmd/tetris` 的責任邊界。
- 補上或更新必要測試，確保清理後核心規則與現有執行流程仍可通過驗證。
- 若發現看似未使用但其實承擔未來近期需求的結構，改為明確保留並加註用途，而不是盲目刪除。

## Capabilities

### New Capabilities
- `code-hygiene`: 規範專案在清理未使用代碼後，仍需維持可建置、可測試，且不保留無引用的核心邏輯路徑

### Modified Capabilities

## Scope

- 玩家目標：玩家可見的玩法、分數、等級、方塊操作、暫停與重新開始行為維持不變。
- 工程目標：讓核心規則、輸入、渲染與啟動流程只保留仍被實際使用的代碼與設定，減少後續實作時的認知負擔。
- 影響範圍：`internal/game`、`internal/app`、`internal/input`、`internal/render`、`cmd/tetris`，以及必要的測試與文件。

## Non-Goals

- 不新增新的玩法功能、控制方式、UI 畫面資訊或平台支援。
- 不重寫既有架構，也不為了「可能未來會用到」而預先抽象介面。
- 不變更 `playable-core-loop` 已承諾的玩家行為需求，除非清理過程發現現況與 spec 不一致並另行提出變更。

## Impact

- 受影響系統：核心規則模組、應用更新迴圈、輸入輪詢、渲染輔助與程式入口。
- API 影響：以內部 API 精簡為主，不預期新增對外介面；若有移除或改名，應一併更新所有呼叫端。
- 相依性影響：不預期新增第三方依賴。

## Risks

- 誤刪目前雖少量使用但具必要語意的代碼，可能造成隱性行為退化。
- 清理過程若同時合併多個責任調整，可能讓 diff 過大而不利審查。
- 若測試覆蓋不足，未使用代碼與必要代碼的界線可能被誤判。

## Validation

- 執行 `gofmt`，確保清理後的 Go 程式碼格式一致。
- 執行 `go test ./...`，確認核心規則與現有模組整合未被破壞。
- 進行一次手動遊玩檢查，確認開始遊戲、移動、旋轉、加速下落、暫停、重新開始與遊戲結束流程維持正常。
