## Context

目前專案由 `cmd/tetris` 啟動，透過 `internal/app` 串接 `internal/game`、`internal/input` 與 `internal/render`。核心玩法已可編譯並通過既有測試，但專案剛完成第一輪核心規格建立，容易留下早期嘗試時未再使用的設定欄位、輔助函式、型別或分支。

這類未使用代碼的問題不在於立即造成錯誤，而在於後續修改時會模糊真正的責任邊界。對目前這種仍在快速演進的 Go 專案，與其保留「也許之後會用到」的結構，不如把仍然需要的資料流與控制流收斂到最小集合，並用測試保護既有玩法。

## Goals / Non-Goals

**Goals:**
- 找出並移除目前未被引用、無實際用途或已被取代的生產代碼。
- 保持 `internal/game`、`internal/app`、`internal/input`、`internal/render` 與 `cmd/tetris` 的依賴關係清楚且必要。
- 在清理過程中維持現有玩法規則、輸入反應與畫面呈現不變。
- 用自動化測試與最小手動驗證確認清理沒有引入退化。

**Non-Goals:**
- 不引入新功能、控制方式、出塊規則或 UI 版面調整。
- 不因清理需求而重做整體架構或新增抽象層。
- 不以暫時註解取代真正移除，避免保留另一種形式的死代碼。

## Decisions

### 決策 1：以呼叫鏈與資料流盤點未使用代碼，而不是只看檔案層級

做法：
- 從 `cmd/tetris/main.go` 的啟動路徑往下追蹤到 app、game、input、render。
- 盤點未被任何生產路徑引用的函式、方法、欄位、常數與設定值。
- 對測試專用結構與正式執行路徑分開判斷，避免誤刪測試支撐代碼。

理由：
- 單看檔案是否存在，無法判斷某些型別或設定是否仍承擔資料傳遞責任。
- 以呼叫鏈為中心較能避免把「低頻但必要」的代碼誤判成垃圾。

替代方案：
- 只依靠人工全文搜尋。
  缺點是容易遺漏由介面、方法值或測試間接引用的路徑。

### 決策 2：優先刪除未使用代碼，其次才是重新命名或註解保留

做法：
- 若結構在目前 proposal 範圍內沒有實際呼叫點或明確近期用途，直接移除。
- 若結構是測試穩定性或後續既定任務所依賴，則保留並讓名稱或註解說明用途。

理由：
- 這次變更的主要目標是降低維護噪音，而不是把噪音重新包裝。
- 保留未使用代碼通常會讓後續開發者誤以為該結構仍是正式契約的一部分。

替代方案：
- 將疑似未用代碼先標記 TODO。
  缺點是問題會累積，且沒有真的降低系統複雜度。

### 決策 3：以最小驗證集合保護清理成果

做法：
- 執行 `gofmt` 與 `go test ./...` 作為基本門檻。
- 若清理影響輸入輪詢、更新迴圈或渲染輔助，再補一輪手動遊玩流程驗證。

理由：
- 這次不是玩法擴充，驗證重點在「沒有壞掉」而不是新增情境覆蓋。
- 專案目前測試集中在 `internal/game`，搭配手動檢查足以覆蓋 app/input/render 的整合風險。

替代方案：
- 在這次變更同步建立大量 UI 整合測試。
  缺點是會放大清理工作範圍，偏離本次目標。

## Risks / Trade-offs

- [誤刪低頻但必要的代碼] → 先用呼叫鏈盤點，再以 `go test ./...` 與手動遊玩檢查驗證。
- [清理幅度過大導致 review 困難] → 以模組分批處理，優先刪除明確無引用結構，避免順手重構不相干邏輯。
- [測試不足導致 app/render 問題漏出] → 對非核心邏輯增加最小人工驗證步驟，至少覆蓋啟動、輸入、暫停、重開與結束畫面。

## Migration Plan

- 先盤點各模組的公開與私有結構，標記無引用候選項目。
- 依模組逐步刪除或收斂未使用代碼，確保每一步仍可編譯。
- 執行 `gofmt` 與 `go test ./...`。
- 完成一次手動遊玩驗證後再合併。

回滾策略：
- 若清理後發現玩家流程退化，優先回復該模組的最後一筆清理提交，再重新縮小變更範圍。

## Open Questions

- 是否已有使用中的靜態分析工具可輔助盤點未使用代碼；若沒有，本次先以編譯器、全文搜尋與測試為主。
- 某些目前未使用但屬於預期近程功能的欄位，是否應在本次一併移除，或另外以明確 change 追蹤其未來用途。
