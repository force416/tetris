## Context

目前專案已定義方向與限制，但尚未有可實際遊玩的版本。這次第一個變更需要建立完整的垂直切片，用來驗證架構是否合理、macOS 上的基本遊玩體驗是否成立，以及後續擴充所需的可測試接縫。

核心限制是：遊戲規則必須能在不啟動圖形介面的情況下測試，同時最終成品必須是 macOS 視窗應用程式，而不是 terminal 介面。因此第一版實作即使規模不大，也需要清楚分離規則運算、應用程式協調層，以及渲染與輸入轉接層。

## Goals / Non-Goals

**Goals:**
- 交付一個支援核心移動與進程的最小可玩 Tetris 迴圈。
- 交付一個會開啟獨立視窗的 macOS 桌面版本，而不是 terminal 版本。
- 定義不把所有邏輯堆進 `main.go` 的基本目錄與封裝方式。
- 讓棋盤更新、方塊生命週期、計分與遊戲結束判定保持可重現且可用單元測試驗證。
- 讓渲染與輸入處理維持為包裹中央遊戲狀態的薄層轉接。

**Non-Goals:**
- 超出清楚可玩棋盤與 HUD 之外的視覺包裝。
- 網路功能、資料持久化、音效系統或排行榜。
- 暫存方塊、鬼影方塊、或完整對齊官方 guideline 的 wall kick 行為，除非它們是穩定基本體驗所必需。

## Decisions

### Decision: 將專案分為 app、game、input、render 四層
實作應將遊戲規則放在 `internal/game`，執行期協調放在 `internal/app`，輸入映射放在 `internal/input`，畫面繪製放在 `internal/render`。

理由：
- 可以保留不依賴視窗或鍵盤的規則測試能力。
- 讓未來更換渲染/輸入方案時，不必重寫核心規則。

考量過的替代方案：
- 為了求快把所有程式都塞進入口點。放棄，因為後續將難以隔離責任與撰寫測試。
- 一開始就為每個邊界都抽介面。放棄，因為在需求尚未證明之前會引入過多抽象。

### Decision: 以顯式狀態機搭配 tick 與 command 更新玩法
遊戲核心應暴露狀態物件，並提供基於時間 tick 與玩家 command 的更新操作，例如左移、右移、旋轉、加速下落、暫停與重新開始。

理由：
- 以 tick 驅動更新很適合 Tetris 的重力與鎖定節奏。
- Commands 可在沒有 UI runtime 的情況下直接被單元測試驗證。
- 輸入處理會退化為 command 轉譯，而不是任意共享狀態修改。

考量過的替代方案：
- 讓 renderer 擁有遊戲迴圈並直接修改共享狀態。放棄，因為會把畫面更新節奏與規則綁死，讓測試變脆弱。

### Decision: 將可調玩法常數集中管理
棋盤大小、重力間隔、計分獎勵與等級提升規則應集中定義在遊戲核心的設定區域。

理由：
- 避免規則與 UI 程式散落硬編碼數值。
- 讓平衡調整與測試更容易。

考量過的替代方案：
- 在各規則函式內直接寫常數。放棄，因為容易造成規則漂移與不一致。

### Decision: 以明確形狀定義與旋轉狀態表示 Tetromino
每個 Tetromino 都應有穩定的身分，以及以一致座標形式表示的有限旋轉狀態集合。

理由：
- 一致的形狀資料能降低碰撞與渲染上的歧義。
- 旋轉測試可以直接驗證每個狀態實際占用的格子。

考量過的替代方案：
- 只在渲染邏輯中隱含表示形狀，或完全依賴程序性轉換。放棄，因為這會模糊規則正確性。

### Decision: 為出塊流程保留可重現的隨機接縫
核心應接受可替換的隨機來源或簡單生成器抽象，讓測試能穩定控制出塊順序。

理由：
- 出塊順序會直接影響生成、計分與遊戲結束情境的測試。
- 可以避免整合測試因隨機性而不穩定。

考量過的替代方案：
- 在核心內直接呼叫全域隨機來源。放棄，因為不利於重現測試結果。

### Decision: 使用桌面視窗遊戲框架而非 terminal UI
第一個可玩版本採用 Go 的桌面遊戲框架來建立圖形視窗、處理鍵盤事件與更新畫面，不使用 terminal/TUI 方案。

理由：
- 這符合專案目標，即交付 macOS 應用程式而非 command-line 工具。
- 可保留 `internal/game` 作為純規則層，僅替換 app/render/input 實作。
- 桌面視窗更符合後續擴充視覺、動畫與資源管理的方向。

考量過的替代方案：
- 使用 terminal UI 快速做原型。放棄，因為不符合產品型態。

### Decision: 第一版 UI 保持最小但完整
第一個可玩版本只需要清楚顯示棋盤、正在下落的方塊、已鎖定方塊，以及包含分數、等級與下一個方塊的 HUD。

理由：
- 先驗證整個遊戲迴圈，而不是把時間花在規則尚未穩定前的視覺包裝。
- proposal 的焦點是最小可玩基線，不是美術完成度。

考量過的替代方案：
- 等所有規則都定案後才做 UI。放棄，因為需要先透過最小端到端體驗驗證操作回饋與遊玩性。

## Risks / Trade-offs

- [渲染/輸入框架的選擇可能限制未來可攜性] → 採用輕量方案，並把依賴隔離在 app/render/input 層。
- [簡化版旋轉行為可能不符合玩家預期] → 在 spec 中明確記錄第一版旋轉規則，並讓形狀模型保有擴充空間。
- [若 tick 時序與畫面更新耦合過深，遊戲節奏會不穩] → 以顯式 tick 推進規則，而不是直接依賴 frame callback。
- [早期的 package 結構可能過薄或過碎] → 先維持少數明確模組，只有在重複壓力出現時才補介面或再拆分。

## Migration Plan

這是全新的玩法基線，沒有既有線上版本需要遷移。

實作順序：
1. 建立 package 骨架與入口點串接。
2. 實作遊戲狀態模型、方塊定義與規則轉移。
3. 加入最小可玩的視窗渲染與鍵盤輸入轉接層。
4. 補上核心規則自動測試與遊玩手動驗證清單。

回退策略：
- 若渲染/輸入依賴不適合，保留 `internal/game`，只替換 app/render/input 層。
