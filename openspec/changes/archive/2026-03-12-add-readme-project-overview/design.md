## Context

目前倉庫已具備可執行的 Tetris 遊戲入口、核心規則模組、輸入輪詢與渲染層，也有 `Makefile` 與 OpenSpec 規格可作為開發與驗證依據；但根目錄缺少 README，導致專案對外沒有一份集中、可信的總覽文件。這次設計的重點不是增加新系統，而是定義 README 的資訊來源與組織方式，避免文件描述超出程式碼現況。

README 需要同時服務兩種讀者：
- 第一次進入倉庫的開發者，想快速知道專案是什麼、怎麼跑起來。
- 後續維護者，想確認 README 是否仍與目前的規格、命令與模組邊界一致。

限制條件如下：
- 內容必須以繁體中文為主。
- 不能把尚未實作的功能寫成已存在能力。
- 說明應優先依據實際程式碼入口、`Makefile` 命令與既有 OpenSpec 規格。

## Goals / Non-Goals

**Goals:**
- 建立一份可放在倉庫根目錄的 README，完整說明專案定位、目前功能範圍與開發入口。
- 讓 README 能對齊現有程式結構，清楚描述 `cmd/tetris` 與 `internal/*` 模組的職責分工。
- 定義 README 應涵蓋的最小資訊集合，讓未來更新時有一致標準。

**Non-Goals:**
- 不建立額外的文件站、教學網站或發行說明流程。
- 不修改遊戲玩法、操作、測試架構或打包流程。
- 不在 README 中設計超出當前程式碼與規格的產品路線圖。

## Decisions

### 決策：README 以「專案定位 + 開發入口 + 結構導覽」為主軸

README 將優先回答三個問題：這是什麼專案、目前能做什麼、如何在本機執行與驗證。這比完整羅列所有內部細節更重要，因為 README 的主要職責是讓讀者快速建立正確心智模型。

替代方案：
- 只放最短安裝說明。這樣可以快速建立檔案，但仍無法解決新讀者不知道專案範圍與模組分工的問題。
- 把 README 做成完整開發手冊。這會讓文件過重，也提高未來維護成本。

### 決策：功能描述以現有程式行為與 OpenSpec 規格交叉驗證

README 中對玩法與功能的描述，應以 `cmd/tetris/main.go`、`internal/app` 的遊戲迴圈、`Makefile` 的可用命令，以及 `openspec/specs/playable-core-loop/spec.md` 所界定的核心能力為準。這能降低 README 說明落後或超前於實作的風險。

替代方案：
- 只依實作者記憶手寫 README。速度快，但最容易出現與程式不一致的描述。
- 只引用規格，不看程式與命令。這會忽略目前實際可執行入口與開發體驗。

### 決策：README 明確區分「已支援能力」與「未涵蓋內容」

README 需要說清楚專案目前聚焦於可玩的核心迴圈、基本操作、分數與等級等內容，並避免暗示已有多人模式、排行榜、帳號或其他延伸功能。這能保護文件可信度，也讓讀者理解專案目前成熟度。

替代方案：
- 省略限制與未涵蓋內容。這樣會讓 README 看起來更精簡，但讀者容易誤判專案範圍。

### 決策：模組導覽以責任邊界描述，不複製程式細節

README 應說明各主要目錄的責任，例如 `internal/game` 負責規則與狀態、`internal/app` 負責應用迴圈與時間推進，但不應複製細節到函式層級。這樣能保持可讀性，也降低未來因程式內部重構而頻繁修改 README 的成本。

替代方案：
- 列出所有檔案與型別。資訊量大，但訊噪比低，且容易過時。

## Risks / Trade-offs

- [README 內容過度承諾] → 以現有程式碼、`Makefile` 與 OpenSpec 規格逐項對照，避免寫入未實作能力。
- [README 過於簡略，仍無法幫助新讀者] → 至少涵蓋專案定位、功能摘要、執行方式、測試方式與模組導覽。
- [README 與未來實作逐漸脫節] → 在任一改變使用方式、專案結構或核心功能對外描述的變更中，同步檢查 README。

## Migration Plan

1. 建立根目錄 `README.md`。
2. 依本設計填入專案定位、功能摘要、開發與驗證命令、模組結構與目前限制。
3. 以人工方式對照 `Makefile`、程式入口與 OpenSpec 規格，修正文案不一致之處。

本變更不涉及資料遷移，也沒有回滾風險；若 README 內容有誤，回退方式是直接修正文件。

## Open Questions

- README 是否需要納入實際按鍵操作對照表，或只描述目前支援的操作類型即可。
- README 是否要直接連到 OpenSpec 目錄，作為需求與設計來源的入口。
